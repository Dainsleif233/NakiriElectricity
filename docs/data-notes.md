# 采集与统计口径说明

这份文档解释「为什么采集脚本和统计逻辑是这样写的」，面向修改本项目的人。
所有参数都来自对 `public/data.json` 真实读数的统计（2026-05-29 ~ 2026-10-16，原始 680 条采样），
运行 `npm run analyze` 可以随时复现这份报告。

## 实测特征与对应决策

| 特征 | 实测结果 | 带来的设计决策 |
|---|---|---|
| 读数分辨率 | 680/680 条读数为整数 → **1 kWh 台阶** | 判定「变化」用 `CHANGE_EPSILON = 0.05`；页面整数显示，出现小数才保留一位 |
| 更新节奏 | 137 次消耗跳变 / 137 个用电日 ≈ **1 次/天** | 源站每天只结算一次，3 小时采集已经足够；再密只是重复采样 |
| 采样冗余度 | 680 条里有 528 条（**78%**）与上一条数值完全相同 | 只有数值变化的读数才进 history：`data.json` 从 680 条降到 **152 条**（13.6 KB） |
| 存活 vs 数据 | 把「没停电但没用电」也写成数据点，图上就会出现水平线 | 存活标记单独放 `room_info.lastCheckedAt`（12h 心跳），history 与图表只承载真实变化 |
| 结算时刻 | 137 次下降跳变的观测区间交集落在本地 **05:00**（127/137 支持） | 「用电日」按本地 05:00 换日；否则「昨日消耗」会整体错一天 |
| 跳变观测延迟 | 原始采样间隔 p50 4.3h、p90 8.0h、最大 23.8h | 跳变的**发生时刻**只能确定在 `(上次读数, 本次读数]` 内，脚本按此维护结算口径 |
| 充值 | 14 次上升跳变，多发生在余额低位 | 上升 = `充值 − 期间消耗` 的净跳变，无法反推精确充值额，页面统一标 `≈` |
| 空提交 | 近 80 次数据提交里 **68%** 只新增了重复值 | 未变化时不改写文件，同时把 cron 挪出 `:00` 整点（定时任务拥堵会让运行被推迟 1~2h） |

## 存储格式

```json
{
  "room_info": {
    "roomId": "1-1-101",
    "displayName": "校本部-C区-1-1-101",
    "updatedAt": "…",      // 读数最后一次「发生变化」的时刻
    "lastCheckedAt": "…"   // 最后一次成功采集的时刻（数值没变时也会刷新）
  },
  "history": [
    { "timestamp": "…", "room_id": "1-1-101", "kWh": 348, "src": "start" },
    { "timestamp": "…", "room_id": "1-1-101", "kWh": 341, "src": "change" }
  ]
}
```

- history 每条占一行，git diff 只会新增一行；`src` 取 `start` / `change`。
- **history 里不会出现同值记录**：数值没变时脚本要么完全不写盘，要么（距上次写盘超过 12h）只刷新 `lastCheckedAt`。
- 前端兼容旧格式：历史里的同值条目会在绘图前被折叠，`lastCheckedAt` 缺失时回落到 `updatedAt`。

## 口径约定

- `kWh` 是**剩余电量**：下降 = 用电，上升 = 充值。
- 用电日按**本地 05:00** 换日。跳变只能确定发生在 `(上次读数, 本次读数]` 内，
  落在区间内最近一个边界结算的是**前一个**用电日。
- 「近 24 小时消耗」「7 天日均」等滚动窗口锚在**最后一次成功采集**（`lastCheckedAt`），
  而不是最后一次数值变化 —— 用后者会把前一天的跳变也圈进 24h 窗口（实测 8 kWh 会被算成 17 kWh）。
- 「数据陈旧」判断同样以 `lastCheckedAt` 为准（阈值 24h）：假期几天不跳变是正常的，不该报陈旧。

## 不变量（均有测试覆盖）

1. **压缩无损**：`compactHistory()` 只删重复采样，`buildSteps()` 的跳变序列逐条一致（151 条逐条校验）。
2. **账目自洽**：累计消耗 − 累计充值 == 首末读数差（实测 1618 − 1321 = 348 − 51）。
3. **口径一致**：采集脚本、前端、数据报告、阈值告警共用 `src/lib/electricity.js` 这一份领域逻辑。

## 脚本

| 命令 | 作用 |
|---|---|
| `node scripts/scrape.js` | 采集一次：数值变了才写 history；没变则按 12h 心跳刷新 `lastCheckedAt`，否则完全不写盘 |
| `node scripts/scrape.js --dry-run` | 只抓取与判定，不写文件 |
| `node scripts/analyze-data.js [--json]` | 数据特征与质量报告，CI 里写入 Step Summary 并在异常时 `::warning::` |
| `node scripts/compact-data.js [--write]` | 把历史压成「只留变化」；写入前强制校验跳变序列等价 |
| `node scripts/check-threshold.js` | 阈值判断，区分「刚刚跌破」与「持续偏低」，并给出预计可用天数 |
| `npm test` | 38 项单测与采集端到端测试（含真实数据不变量、网络失败容忍与线上契约守护） |

## 已知限制

- **结算小时无法再从存储反推**：history 只存变更点，相邻条目间隔 ~24h，任何时刻都落在每个跳变的观测区间内，
  估计值会退化成 0:00。`DAY_BOUNDARY_HOUR = 5` 来自原始逐次采样的统计，由合成数据测试守护。
- **跳变间隔 >24h 不等于漏采**：可能是「当天没用电」。能反映漏采的是采集间隔本身，
  因此该判断放在采集时刻（距上次 `lastCheckedAt` >24h 时告警），而不是对历史做统计。
- 采集脚本的失败是显式的：令牌失效、响应不是 JSON、`data.json` 解析失败都会以非 0 退出码结束并让 job 变红，
  且**绝不**改写已有的 `data.json`。
- **网络层失败（`fetch failed`）是唯一的例外**：DNS/连接被拒/超时这类抖动按「跳过一次采样」处理 —— 退出码 0、
  不写盘，只在 Step Summary 和 `::warning::` 里留痕（`scrape_status=network-failed`）。代价是偶发断流不会立刻报警，
  所以用 `lastCheckedAt` 兜底：距上次成功采集超过 48h（`NETWORK_FAILURE_GRACE_HOURS`）仍然判红。
  诊断看日志里 `error.cause` 的错误码（如 `ECONNREFUSED`），外层永远只有 `TypeError: fetch failed`。
- **源站响应结构**：`ykt.ujs.edu.cn/charge/feeitem/getThirdData` 成功时 `map.showData` 为包含房间与余额文本的对象（不是布尔 `true`），实际数值读数位于 `map.data.lastSd`。参数不匹配时为 `false`。采集校验必须使用真值判断，不可强比布尔值。
